# AgentCyTE 贯通指导使用说明

> 完整链路实测验证版：**XML → AgentCyTE(CLI/Web) → CORE daemon(gRPC) → core-http-bridge(HTTP 双入口确认)**。
> 环境：AgentCyTE 离线包 venv 版（内置 vendor/core 9.2.1），宿主 core-daemon(127.0.0.1:50051)，core-http-bridge(8080)。

---

## 0. 部署形态速览

```
┌────────────────────┐   XML 文件    ┌──────────────────────┐   gRPC    ┌─────────────────┐   HTTP    ┌──────────────────┐
│ 编写/编辑场景 XML    │ ──────────▶ │ AgentCyTE            │ ────────▶ │ CORE daemon     │ ────────▶ │ core-http-bridge │
│ (Node Info/Routing/ │  上传/读取   │ (.venv, 内置 vendor/ │  50051    │ (宿主, 建会话)   │   8080    │ (查/删会话/节点)  │
│  Services 等 section)│             │  core 客户端)        │           │                 │           │                  │
└────────────────────┘             └──────────────────────┘           └─────────────────┘           └──────────────────┘
```

- 角色解析、路由规划在 XML section 里声明，AgentCyTE 负责解析并 gRPC 推给 core。
- core-daemon 真正创建会话；core-http-bridge 提供 HTTP 视角查看/删除该会话（与宿主持有状态一致）。

## 1. XML 场景文件构造（关键：section 名必须匹配 AgentCyTE 解析器）

AgentCyTE 按**固定 section 名**解析 XML，写错名字就静默 fallback（节点变默认 10 台 Workstation、路由器不生效）。

### 最小可用模板

```xml
<?xml version="1.0" encoding="UTF-8"?>
<Scenarios>
  <Scenario name="my-scenario" scenario_total_nodes="6" base_nodes="6">
    <ScenarioEditor>
      <BaseScenario filepath=""/>

      <!-- 1) Node Information: 声明参与节点角色 + 数量 -->
      <section name="Node Information" base_nodes="6" density_count="6">
        <item selected="Router"     v_metric="Count" v_count="2"/>
        <item selected="Workstation" v_metric="Count" v_count="4"/>
      </section>

      <!-- 2) Routing: 声明路由协议 + 路由器数量（有它才建“真路由器”带服务） -->
      <section name="Routing" density="1.0">
        <item selected="OSPFv2" v_metric="Count" v_count="2" r2s_mode="Exact" r2s_edges="2"/>
      </section>

      <!-- 3) Services(可选): 给主机分配服务; 不写则路由服务也由 Routing 决定 -->
      <section name="Services" density="1.0">
        <item selected="SSH" v_metric="Count" v_count="4"/>   <!-- 4 台主机都带 SSH -->
      </section>

      <section name="Notes"><notes>说明文字</notes></section>
    </ScenarioEditor>
  </Scenario>
</Scenarios>
```

### section 语义速查（实测核实）

| section | 作用 | 关键字段 | 说错/缺省的后果 |
|:--|:--|:--|:--|
| `Node Information` | 定义角色与数量 | `<item selected="Router" v_metric="Count" v_count="2">`；`base_nodes`/`density_count` 控总节点数 | 缺 → 默认 10 Workstation |
| `Routing` | **关键**：声明路由协议与路由器数 | `<item selected="OSPFv2" v_metric="Count" v_count="2" r2s_mode="Exact">` | 缺 → router 成普通 PC 节点（无 zebra/OSPF），拓扑走扁平 star |
| `Services` | 给主机分配服务 | `<item selected="SSH" v_metric="Count" v_count="4">` | 缺 → 主机只有默认服务 |
| `Routing` 的 `r2s_mode` | 路由器↔交换机聚合策略 | `Exact` = 精确；`r2s_edges` 控每路由挂交换机数 | 影响网段分配 |

### 角色类型（`selected` 合法值，map_role_to_node_type）
`Router` / `Switch` / `Hub` / `Wireless` / 其它 → 默认 PC。
注意 CORE 9.2 协议里**没有独立 ROUTER 节点类型**，路由器是通过「默认 PC 节点 + IPForward/zebra/OSPF 服务」表达的 —— AgentCyTE 在 segmented 路径里自动加。

## 2. 推送场景到 CORE

### 2.1 通过 CLI（直连，最直接）

- `CORE session started`
- `[router.plan] ... final=2`（路由计划）、`building segmented topology with routers`（说明走的是真路由器路径）

- 规划预览（不真实建会话）：`POST /api/plan/preview_full` `{"xml_path": "...", "seed":42}`

## 2.3 通过 AgentCyTE 自身 HTTP API 推送（端到端实测）

> 此链路完整验证过：`login → run_cli_async → run_status → CORE 建会话`，双入口（bridge + 宿主 GetSessions）逐字段一致。

**⚠️ 核心前提（已内置脚本，但要知道原理）：CLI 子进程必须用 venv 解释器。**
`run_cli_async` 会另起 CLI 子进程推 topology，解释器由 `webapp/app_backend.py: _select_python_interpreter()` 挑选，优先级：
`CORE_PY` 环境变量 → `core-python` → `python3` → `python` → `sys.executable`。
系统自带的 `/usr/bin/python3` 缺 `google`(protobuf)，只装在 venv 里 → 子进程 `import core.api.grpc` 失败 → 全程走 **offline report-only**（CLI log 出现 `core.api.grpc not available`，不建任何 CORE session）。

**修复（脚本层，已落地）：离线包 `run.sh` 已内置 `export CORE_PY="$VENV_DIR/bin/python3"`**——正常用 `bash run.sh` 起服务即可，无需手动设。只有绕过 run.sh 直接 `python3 main.py` 启动时才需要手动：
```bash
CORE_PY=$PKG/.venv/bin/python3 PYTHONPATH=$PKG/vendor nohup $PKG/.venv/bin/python3 main.py &
```

### 完整 HTTP 流程（curl）
```bash
B=http://127.0.0.1:9093
curl -s $B/healthz                          # ok, 200
curl -s -c /tmp/c -d "username=coreadmin&password=coreadmin" $B/login   # 302 建 cookie
RUN=$(curl -s -b /tmp/c -F "xml_path=$PKG/scenario.xml" \
          -F "host=127.0.0.1" -F "port=50051" $B/run_cli_async)
# {"run_id":"<uuid>"}
for i in $(seq 1 8); do sleep 2; curl -s -b /tmp/c $B/run_status/<run_id>; done
# done=true, returncode=0 → 子进程完成真推送
```

### 确认生效的证据（CLI log `cli-<run_id>.log`）
- `Using python interpreter: .../.venv/bin/python3`（必须，不是 `/usr/bin/python3`）
- `[router.plan] ... final=2`、`building segmented topology with routers`
- `add_node id=1 name=router-1 type=DEFAULT`、`add_link`（真路由器 + 链路）
- `CoreGrpcClient.start_session() ok`、**`CORE session started`**（这才是真建会话）

### 实测结果（20 节点场景）
- **入口 B**：`GET http://127.0.0.1:8080/api/sessions` → `[{"id":1,"state":4,"nodes":20,"dir":"/tmp/pycore.1"}]`
- **入口 A**：宿主原生 `GetSessions` → `session id=1 state=4 nodes=20 dir=/tmp/pycore.1`（**与 B 完全一致**，证明 HTTP API 链路对宿主 CORE 真实生效）
- 节点构成：真路由器 `router-1/2` + 交换机 `rsw-1-1..2-2` + 工作站 `workstation-1-1..2-5`（5 台主机分到 2 路由网段）

### 验证后清理
```bash
curl -s -X DELETE http://127.0.0.1:8080/api/sessions/1   # 删会话
curl -s http://127.0.0.1:8080/api/sessions                # → [] 无残留
ps -eo pid,args | grep 'vcmd.*pycore' || echo no-vcmd      # 无 vcmd 残留
kill -9 <主进程 pid>  # 停服务; 用 pgrep -f main.py 逐个杀,勿用 pkill -f 自身
```

## 4.5 常见疑问（FAQ，实测结论）

### Q1：会话 id 和节点 id 从哪拿？AgentCyTE 的接口能拿到吗？

**会话 id / 节点 id 由 CORE 分配，AgentCyTE 自身没有「查询会话/节点」的只读接口**（它的 HTTP API 只有生成/上传/运行/下载报告）。三个可靠途径：

1. **部署 XML（AgentCyTE 每次运行写入 `outputs/core-sessions/`）**
   ```text
   core-session-1-20260910-100055-session-deployed.xml
   ├─ 文件名里的数字 "1"  = 会话 id
   └─ <link node1="3" node2="17"> 里的数字 = 节点 id
   ```
2. **core-http-bridge（HTTP，最方便）**
   ```bash
   curl -s http://127.0.0.1:8080/api/sessions/1 | python3 -m json.tool
   # 节点数组里每个元素带 "id"、name、type、services；另有 "links" 数组，含 node1_id/node2_id
   ```
3. **CORE 原生 GetSession（字段名别写错）**
   ```python
   c.stub.GetSession(core_pb2.GetSessionRequest(session_id=1))   # 注意是 session_id，不是 id
   ```

> AgentCyTE 有个 `/core/start_session` 路由，但它是**接收前端传来的 session_id 去调 start**，不是查询接口，不能帮你查 id。

### Q2：XML 里没有链路数据，链路哪来的？

**链路不是从你的 XML 读的，是 AgentCyTE 按拓扑规则现场生成、逐条 add_link 推给 CORE 的。**
XML 只声明**角色与数量**（2 Router + 5 Host + OSPFv2），`build_segmented_topology`（有 Routing section 才走）在内存里建图：
- 建真路由器 → 每台挂 `r2s_edges` 个交换机
- 主机按密度/网段挂上
- `session.add_link(node1=..., node2=...)` 逐条写入

本次实测（20 节点场景）链路数量四个来源印证：
- CLI log：`Session.add_link() ok` 33 条调用、去重后 `links_list=19`
- 部署 XML：`<link>` 元素 20 条
- bridge `/api/sessions/1` 的 `links`：**19 条**
- CORE 原生 `GetSession().links`：**19 条**，node1/node2 与 bridge 逐条一致

（19 vs 20 的 1 条差异是计数口径/重复链接引起，非缺失。）

**CORE 只显示节点没链路时排查**：
1. **没加 `<section name="Routing">`**（最常见）→ 走 `build_star_from_roles`，建普通 PC、拓扑扁平，链路少得几乎看不到。补 Routing 才建真路由器+交换机+有网段的链路。
2. 看 CLI log 的 `add_link` 数：若 `add_node` 有但 `add_link` 为 0，是 builder 没生成链路。
3. 已推但没生效：检查会话 `state` 是否为 4（RUNNING）；没 start 前链路不下发到运行态。
4. 用 bridge 的 `links` 数组长度核实（不是看前端画布，画布可能按 canvas 过滤）。

### Q3：XML 声明的节点数与生成拓扑的数量一致吗？

**不一定一致，且通常会「超标」——因为 XML 的数量是「密度基线」，不是「总节点硬上限」。**
例：`scenario_total_nodes="7" base_nodes="7"`（2 Router + 5 Host）实测生成 **20 节点**（2 Router + 4 Switch + 14 Host）。
CLI 规划日志（`router_plan` / `segmented`）：
```
hosts=14  routers=2     ← 最终规划（不是 XML 的 5 host）
segmented) routers=2 hosts=14 links_list=19 attempts=33 success=33 fail=0
Session(id=1) nodes 20  ← 2 + 4 + 14 = 20
```
**构成拆解**：
- Router = Routing 的 `v_count`（additive，不受 base 影响）
- Switch = `r2s_edges`（每路由挂 2 个交换机 → 2×2=4）
- Host = 按密度往网段补齐（base 7 被展开到 14）

**想让生成数量 = 声明数量**：
1. 调低 `density`（`base_nodes`/`density_count`）→ Host 补齐量减少
2. 收紧 `r2s_edges`（2→1）→ Switch 减少
3. **CLI 加 `--max_nodes N` 硬上限**：`min(base_total, max_nodes)`（cli.py:394）
4. 先预览再跑：`POST /api/plan/preview_full {"xml_path":"...", "seed":42}`，响应里 `effective_total_nodes` 就是最终数，调到目标再 run

> 语义记住：**声明数量只约束 Router/Switch 相对比例 + Host 密度；最终总节点 = 2×router + r2s_edges×routers + host密度展开。**

### Q4：XML 里加了 Traffic / Segmentation / Wireless 后，CORE 会话停在 CONFIGURATION 不运行？

**是的——有 3 个 section/角色会触发「会话推到 CORE 后停在 CONFIGURATION(state=2，不进 RUNTIME=4)」：`Traffic`、`Segmentation`、以及 `Wireless` 角色。** 其余 section 均不影响启动（实测矩阵，每次全新会话 + 干净 core-daemon 验证）：

| section / 角色 | start_session 耗时 | 会话状态 |
|:--|:--|:--|
| **Traffic** section | ~1.1–1.7s（异常快） | **CONFIG ❌** |
| **Segmentation** section | ~1.7s | **CONFIG ❌** |
| **Wireless 角色**（WIRELESS_LAN 节点） | ~8.8s（慢但 <10s） | **CONFIG ❌** |
| base（纯 Count） | ~10.4s | RUNTIME ✅ |
| Services（SSH+DefaultRoute+DHCP） | ~10.4s | RUNTIME ✅ |
| Vulnerabilities（Type/Vector + Random） | ~10.6s | RUNTIME ✅ |
| Events | ~7.5s | RUNTIME ✅ |
| Hub 角色 | ~10.5s | RUNTIME ✅ |
| Switch 显式 / Weight / Routing 高级参数 | ~10–11s | RUNTIME ✅ |
| Segmentation 去掉 Traffic 仍卡 | — | 说明是两者各自独立卡因 |

**判定技巧**：正常 RUNNING 的会话 `start_session` 耗时 **~10s**（CORE 要等所有节点配置完成）；停在 CONFIGURATION 的会话耗时 **显著小于 10s**（1–2s 或 8.8s）就提前返回。**通过 `start_session ok in X ms` 即可预测最终状态**：X≈10s 会 RUNTIME，X≪10s 会卡 CONFIG。

**如果你要「全参数且 RUNNING」**：用全部 section，但**去掉 Traffic / Segmentation / Wireless**（这三个留作"仅生成、不运行"的场景或手动单独调），其余（Node Info 全角色含 Hub/Switch、Routing 全参数、Services、Events、Vulnerabilities）可同时使用并正常 RUNTIME。

### Q5：离线环境（core 容器内 + agentcyte 宿主机）下，最大可用参数模板是什么？

实测边界（干净 core-daemon、同一 XML 逐变体验证）：**能 RUNNING 的最大参数组合 = 全部 section + Node Info 全角色（含 Hub/Switch），但 Node Info 不用 Weight 双度量**。

- **✅ RUNNING（23 节点，start ~11.8s）**：Node Info 全 Count（Router 2 + Switch 2 + Hub 1 + Workstation 5），另带 Routing 高级参数（r2s_hosts_min/max + r2r）+ Services（SSH/DefaultRoute/DHCP）+ Events + Vulnerabilities（Type/Vector + Random，无 Specific）。→ 模板见 `docs/examples/scenario-offline-max.xml`。
- **❌ CONFIGURATION（27 节点，start ~2.5s 提前返回）**：同一组合**外加 Node Info 的 Weight 双度量**（Workstation Weight 0.6/0.4）。**Weight 与 Switch/Hub 组合使节点结构 >23 时卡启动**；Weight 单独（无 Switch/Hub，20 节点）反而不卡（见 Q4 矩阵）。
- **vuln 离线可用性**：`Type/Vector` + `Random` **可用**（只打 CVE 标签、不建 docker，不依赖容器内 docker）。`Specific` **慎用**：会解析 `v_path` 生成 DOCKER 节点，core 容器内若无 docker（socket/dind）则该节点起不来、会话卡。离线形态只用 Type/Vector + Random。

**离线形态黄金规则**：Traffic / Segmentation / Wireless 三个不用；Specific vuln 不用；Node Info 别用 Weight 双度量（除非保持结构 ≈20 节点）。其余全保留 → 可 RUNNING。

## 5. 常见坑（实测踩过）

1. **section 名写错 → 静默 fallback**：`Basic` + `role count` 写法不认，节点变默认 10 Workstation。必须用 `Node Information` + `<item selected v_metric=v_count>`。
2. **只有 Node Information、没 Routing → router 是假的**：router 节点建成普通 PC（无 zebra/OSPF），拓扑走 star。补 `<section name="Routing">` 才走 segmented、建真路由器。
3. **gRPC stub 为 None**：CoreGrpcClient 需 `.connect()` 后才暴露 stub。
4. **CoreGrpcClient 构造**：传单字符串 `'host:port'`，不要拆成 `(host, port)`（第二个位置是 proxy 标志）。
5. **宿主 core-daemon 必须 50051 在监听**：`ss -ltn | grep 50051`。
6. **core-http-bridge 与宿主 core 状态一致**：两边看到的会话完全相同（同 id/state/nodes/dir）。
7. **`/run_cli_async` 走 offline 不建会话**：`_select_python_interpreter()` 挑了系统 `/usr/bin/python3`（缺 protobuf）→ 子进程 `import core.api.grpc` 失败。**离线包 run.sh 已内置 `export CORE_PY=$PKG/.venv/bin/python3`（脚本层修复）**；若绕过 run.sh 直跑 main.py，需手动设该变量再触发（详见 2.3）。
